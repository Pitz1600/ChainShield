# Frontend UI conventions

Preserve the existing indigo/violet gradients, dark navigation, white cards, and status colors. No component library or CSS framework is required.

Use the tokens in `frontend/src/index.css`: `--primary`/`--primary-dark` for actions, `--bg-main`/`--bg-card` for surfaces, `--text-primary`/`--text-secondary` for text, `--border-color` for borders, `--radius-*` and `--shadow-*` for shape/depth. `--text-muted` now uses slate 500 rather than slate 400 for readability. The spacing scale is `--space-1/2/3/4/6/8` (4/8/12/16/24/32px at the default font size). Use `--layout-max-width` (1560px) and `--layout-gutter` for page shells. Main feature pages receive the same gutter and maximum width.

Use `.btn-primary` for the main action, `.btn-secondary` for supporting actions, and `.btn-link` for inline actions. Keep explicit disabled states on controls; disabled buttons suppress hover translation and show the disabled cursor. Buttons have a minimum 44px height. Icon controls also need a 44px width and an accessible name. Lucide icons retain their existing per-purpose sizes and strokes; shared CSS prevents flex shrinking and aligns them with text.

Controls inherit the application font and fit their parent. Mobile fields use at least 16px text to avoid input zoom. Associate visible labels with input IDs (or wrap the control in the label); name icon-only buttons with `aria-label`. Validation remains native or uses existing feature logic; error banners announce with `role="alert"`. Loading indicators in the application shell announce with `role="status"`. Keep existing textual status descriptions; never communicate state through color alone.

The shared `.card`, `.badge-*`, and `.section-*` utilities remain available. Success/warning/danger/info badges use tinted backgrounds and dark text. Prefer these conventions for new components; existing feature cards retain their shapes and business-specific contents. Empty, error, loading, and success content remains in the owning feature.

Feature CSS must scope selectors to the owning screen. `:where(.screen-root) .component` deliberately adds no specificity, preserving existing local overrides. Root selectors remain directly targeted. Feedback dialogs also scope to `.feedback-modal-overlay` because they appear from both Transactions and Feedbacks. Keyframe names carry the owning stylesheet name to avoid global animation collisions. Do not reuse a feature's CSS accidentally by relying on navigation having loaded it: Transactions explicitly owns its hero background.

Desktop navigation remains visible above 768px. At 768px and below, it becomes a drawer with a backdrop, body scroll lock, Escape dismissal, focus containment, and inert contents while closed. The menu button uses the layout's state for `aria-expanded` and names its controlled drawer. Resizing to desktop or navigating closes the drawer. The skip link targets the main landmark.

Use the shared `ConfirmModal` for confirmations, including logout. It supplies dialog semantics, title/description associations, focus containment/restoration, body scroll locking, a named close button, and submission states. The feedback composer also uses `useDialogFocus`. Transaction, integrity, profile, and admin overlays use `DialogSurface`, which preserves their existing markup and actions while sharing focus and scroll handling. Confirmation/composer Escape dismissal is disabled while submission is pending. Dialogs stay within the viewport and scroll internally; tables scroll through their existing wrappers. At 768px and below dashboard grids become one column, including cards with desktop grid spans. Respect reduced-motion preferences for animations and transitions.

Do not change APIs, role predicates, authentication decisions, or security validation as part of presentation work. Manual verification and remaining limitations are recorded in `FRONTEND_FIXUP_RESULTS.md`.
